[`design-delta.md`](./design-delta.md) starting from the current state described in

## 1. Scope and how to read this plan

- **The deliverable is the numbered task table in §3.** Tasks are ordered so that
  every task's dependencies appear earlier; the `Depends on` column lists hard
  prerequisites (tasks with disjoint dependencies can run in parallel).
- Each task is roughly **one PR** in its primary repo. Where a task necessarily
  spans two repos (e.g. a DBOS workflow plus its API enqueue endpoint, or an API
  endpoint plus its DTO schemas), the `Repo` column lists both; submodule bumps
  ride along.
- **API DTO Zod schemas** (design-delta §2.11, last row) are added to
  `database-lib` incrementally *by the API/UI task that introduces the endpoint* —
  the DTO's failing parse/reject tests are written in `database-lib` first, then
  the endpoint is built against them. They are not one big up-front task.
- Repo abbreviations: **db-lib** = `supagloo-database-lib`, **api** =
  `supagloo-nodejs-api`, **dbos** = `supagloo-nodejs-dbos`, **nextjs** =
  `supagloo-nextjs`, **root** = `supagloo` (Compose orchestration).

### Test strategy (applies to every task — stated once, not repeated per row)

**TDD rhythm, no exceptions:** every task starts **red** — write the failing unit
tests *and* the failing e2e spec that capture the intended behavior first — then
implements the minimum to go **green**, then refactors with the tests as the
safety net. Nothing merges red. The `Unit tests` / `E2E tests` columns state
*what the tests verify*, not test code.

**Unit tests everywhere:** every task has unit tests (Vitest in every repo,
matching the existing `supagloo-nextjs` setup) — pure logic in isolation, network
and DB mocked/faked.

**What "e2e" means per layer:**

| Layer | E2E definition |
|---|---|
| **db-lib** | Apply real migrations to the Compose Postgres and exercise the generated Prisma client against it: constraint behavior (uniques, composites, FKs), JSON-column round-trips, enum values. No mocks. |
| **api** | Real HTTP calls against a running API instance backed by the Compose Postgres + MinIO. **All** provider egress hits the **real** APIs — OpenRouter/Gloo/YouVersion per design-delta §10, GitHub (api.github.com + github.com) per §11. No in-process mocking; the one named exception is the create-new-repo OAuth token exchange (§11.4 tier 1), where a single injected `fetchImpl` intercepts that one URL and throws on any other. |
| **dbos** | Actually enqueue via `DBOSClient` (workflowID = domain-record id) and run the workflow to completion against the real `supagloo_dbos` system DB + app DB + MinIO. Includes **crash/replay tests** where the design emphasizes recovery: kill the worker mid-workflow, restart, assert completed steps are not re-executed and side effects are not duplicated. |
| **nextjs (UI)** | **Stagehand** specs (existing harness in `tests/e2e/`) driven against the full Compose stack. The existing flag-gated demo/test-session seam is extended (task 23) to obtain a *real* session via the flag-gated `POST /v1/test/seed` endpoint instead of faking browser state — so UI e2e exercises browser → BFF → API → Postgres/MinIO/DBOS for real. Existing mock-session-only specs remain for pure-UI regressions. Playwright is not introduced; Stagehand is the established UI-e2e tool here, and non-UI e2e never uses a browser. **Since task 62 this splits into THREE lanes** (design-delta §11.7): `test:e2e` (mock — Docker-free, no secrets, no network), `test:e2e:real` (real stack + real GitHub), and `test:e2e:render` (the heavy Remotion spec, alone). A unit guard asserts every `tests/e2e/*.e2e.ts` belongs to exactly one lane — a spec in no lane never reports, which is a green-lie generator. |

**Provider egress in e2e** *(policy revised 2026-07-22 by design-delta §10 for
OpenRouter/Gloo/YouVersion, and extended 2026-07-25 by §11 to GitHub — together
these supersede the original "live-provider smoke tests are manual/optional,
never gating" line for **every** provider)*: e2e always exercises the **real
provider APIs** — real-provider e2e *is* the gating suite. An e2e test either
hits the real provider or does not exercise that provider at all; deterministic
provider *misbehavior* (injected failures, controlled timing, error statuses) is
a **unit** concern via injected fetch, never an e2e one (§10.6/§11.6). Required
real secrets come from the root `.env` (tasks 34-E2/34-E8/62); a missing secret
**throws** in e2e setup rather than silently skipping — vitest's default reporter
collapses a skipped file's console output, so a warn-and-skip is invisible (row
56 item 2). The sole exception: interactive browser logins cannot be automated
with static credentials — a spec may shim *only that interactive hop* (YouVersion
OAuth sign-in and OpenRouter's PKCE page per §10.2/§10.4b; GitHub's
create-new-repo user authorization per §11.4, where the shim is one injected
`fetchImpl` intercepting exactly `POST /login/oauth/access_token` and throwing on
any other URL).

**GitHub joined this policy in task 62** (design-delta §11). There is no
`github-stub` and no local git server: `tests/stubs/**` is deleted entirely, all
four repos reach real github.com / api.github.com, the installation id and owner
login are **discovered at run time** (never literals), and fixture repos are
per-run, private, `auto_init` throwaways named `supagloo-e2e-delete-me-*`.
Nothing is torn down in-suite — reclamation is `npm run cleanup:github-e2e`, an
interactive, archive-only human action (row 67). `docker-compose.test.yml`
survives as the **test-enablement** overlay (the `POST /v1/test/seed` gates + the
api's MinIO wiring) and stubs nothing; a permanent inverted unit guard fails if a
stub service or a `GITHUB_*` override creeps back into it.

## 2. Binding constraints honored throughout (from `.claude/agents/tech-lead-memory/`)

- **Static DBOS workflows only**; API enqueues via `DBOSClient` with
  `workflowID` = domain-record id; status flows back via app-DB rows; no HTTP
  between API and DBOS.
- **GitHub App** (not OAuth app): only `installationId` stored; short-lived
  installation tokens minted on demand; every git-ops workflow starts with
  `mintInstallationToken`.
- **Composition source of truth is the repo** (`supagloo.project.json`, Zod-
  validated); no Composition/Scene tables; media in S3 by key.
- **KJV/BSB only** for the generation pipeline; version ids resolved via the
  YouVersion "Get a Bible collection" endpoint at implementation time — never
  hardcoded.
- **OpenRouter covers all media modalities**; AI SDK `generateObject` for
  structured text, plain `fetch` for media; **model ids never hardcoded**
  (discovery endpoints).
- **MinIO local S3 parity** with dual endpoints (`S3_ENDPOINT` /
  `S3_PUBLIC_ENDPOINT`); one Postgres 17 container, two logical DBs.
- **Prisma exact-version pin** in api/dbos, CI-enforced against db-lib's
  exported pin.

    returns **201 with the live, publicly-listed item** (§7, plan row 39), and it
    is deliberately plain CRUD rather than a workflow. The cards presume an
    asynchronous review queue that gates visibility *before* an item is public.
    Building them is therefore a **product decision about whether publishing stops
    being immediate**, not a UI task — and it would need a moderation state that
    `GalleryVisibility` does not have (`public|unlisted` only, D19) plus a removal
    reason and appeal flow (D20). Card 4a was the only one buildable against
    today's contract, which is why it is the only one built.

    - **D9 — `Change cover frame` has no endpoint.** `thumbnailAssetKey` is
      server-recomputed via `buildRenderThumbnailKey` and is explicitly never
      client-supplied, so cover-frame selection does not exist at any layer.
    - **D10 — nothing enumerates the valid translations.** 16b draws
      `TRANSLATION ▾` as a **select**, but `TranslationSchema` is an open
      `z.string().min(1)` with no enum and no list endpoint to populate it.
